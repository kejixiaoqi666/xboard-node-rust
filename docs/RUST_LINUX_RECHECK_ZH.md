# Linux 复验与下一轮优化定位

2026-10-02，按用户要求在美国建站服务器的独立目录完成新一轮验证。原先的 Rust 编译源码、旧/优化二进制与外部 sing-box 均通过哈希回读；本轮追加测试探针、报告和数据，没有修改已验收的运行程序。

## 新一轮结果

环境为 Debian 13.5 / ARM64，6 个逻辑 CPU，约 7.7 GiB 内存。所有测试面板、origin、VLESS 服务端及客户端监听在回环地址；面板凭据和用户为合成数据。证书原地读取，主机 DNS、网络参数及生产服务配置未调整。

- Linux release workspace：**71 项通过**，默认忽略的真实内核项另行显式执行，**1 项通过**；格式检查通过。
- 原优化二进制：**9 项 CLI 验收通过**，涵盖 HTTPS 认证、真实 VLESS 内容、304 不重启、用户替换/旧用户拒绝、不支持的限制拒绝、内核崩溃恢复及 SIGTERM 清理。本次 SIGTERM 约 16 ms。
- 10000 用户，两个版本各连续采样约 **90 秒**。控制程序在各自窗口内 RSS 没有增长；这不构成长期无泄漏证明。
- **256 条真实代理连接同时保持 10 秒**，256 条回复均核对正确。随后并发 8、**1024 次 × 256 KiB** 内容完整通过，内核未换代；内核和控制程序 FD 均回到各自的初始 10。
- 在 **10000 ↔ 20000 用户间更新 6 次**。每次使用更新前无法认证的新 UUID，更新后验证实际 VLESS 响应；后续循环确认上一版 UUID 被拒绝。控制程序维持 2 线程，FD 稳定回到 10，候选配置最终只有 1 份。
- 结束后无本次仍存活的 Rust/sing-box 测试进程；7 个既有服务的 PID/状态、全局 hosts 哈希与所有保留二进制均与测试前一致。

| 控制程序指标 | 保留的优化前版本 | 当前优化版本 |
| --- | ---: | ---: |
| 二进制体积 | 6,623,160 B | 3,676,088 B |
| 10000 用户 RSS 中位数 | 33.33 MiB | 29.82 MiB |
| 控制线程 | 8 | 2 |
| 90 秒窗口 CPU，按一颗核计算 | 0.652% | 0.111% |

这一轮的 CPU 原始增量为旧版 59 ticks、优化版 10 ticks，tick 为 10 ms。持续采样比上一轮短样本更有分辨力，仍只适用于此处的 1 秒无变更轮询负载；两个版本顺序执行、宿主同时运行其他服务，不据此给出统计置信区间。

外部 sing-box 空闲 RSS 约 55.84 / 56.53 MiB；此窗口内记录 0 CPU ticks，只表示低于采样分辨率。Rust 控制层优化没有证明转发层内存或 CPU 同幅度下降。

1024 次回环传输约 135.03 MiB/s，含 Python origin/线程池、客户端和共享宿主成本。没有相同长样本的旧版对照，不用于声明吞吐提升、公网速度或最大承载。

## 明确找到的优化空间

### 1. 减少完整配置生成的中间对象，优先实施

把当前 `SingBoxConfigBuilder::build` 单独放入系统分配器计数探针，每个规模重复 3 次。只测有效 VLESS 配置的构建和 JSON 编码；输入用户表提前创建，计数器记录请求的分配字节，不包括分配器元数据，不等于进程 RSS。结束后全部受测分配均释放为 0，不能据此推断整个进程无泄漏。

| 用户规模 | 最终 JSON | 构建分配次数 | 构建/编码峰值活跃堆字节，排除输入 |
| --- | ---: | ---: | ---: |
| 10000 | 619,107 B | 160,045 | 20.51 MiB |
| 20000 | 1,249,107 B | 320,045 | 41.05 MiB |

实际更新实验的控制程序 RSS 峰值为 **58.30 MiB**，6 次更新并恢复到 10000 用户后约 **42.84 MiB**，高于同实验开始时约 29.39 MiB。说明完整变更路径值得继续优化；6 次循环不足以区分长期泄漏和分配器保留，需要随后更长的有界试验。

具体顺序：先把已拥有的 `Vec<Value>` 移入 inbound/root，避免嵌套 `json!` 再次序列化复制；保持公开 `build` 返回值、用户校验和生成配置兼容。再考虑内部用借用的 `Serialize` 视图直接写候选文件，减少完整 `Value` 与字节缓冲同时存在。`serde_json::to_writer` 支持向输出流序列化，见 [当前锁定版本的官方接口](https://docs.rs/serde_json/1.0.151/serde_json/fn.to_writer.html)。

实施时继续保留 16 MiB 大小限制、候选文件权限、写盘失败清理、外部配置检查、验证成功后激活及旧快照回滚。上述方向**本轮尚未合入**，没有预先承诺降低比例。

### 2. 降低用户更新对连接的影响

更新时保留了 64 条已到达 origin 的连接。新用户认证成功后释放请求，**64 条全部中断，0 条完成原响应**。这是目前同端口 stop/start 的已知行为，这次获得了实际连接证据。

优先设计按内核能力声明的用户增量更新接口；若内核能力不满足，再研究入口监听与工作进程分离、旧连接排空等方案。不能只把强制结束改成 SIGTERM 就称为无中断更新；也不能把任意配置重载接口视为保留旧连接的保证。

需要验收新增/删除用户的认证边界、正在下载的连接、更新失败回滚、停止期间迟到更新和资源回收。此项是后续稳定性工作的明确优先级。

### 3. TCP 和整机内存应单独优化转发层

当前 Rust 程序负责控制，协议转发仍由外部 sing-box 实现。本次新样本未证明数据面存在 CPU 或吞吐瓶颈。后续容量测试应有固定速率与较长窗口，分别统计 Rust、服务端内核、测试客户端、系统 socket 缓冲和 FD，逐级增加实际在线连接；低带宽小机的配置策略还需独立验证。

二进制目前约 3.68 MB，后续可分析依赖与可选功能，但不能把删功能或取消恢复/诊断语义当成同功能优化。更换分配器和构建选项也应作为分别比较的实验项。

## 探针修正与证据

首轮执行到第二次用户更新时，PID/业务响应断言失败，原 driver 退出码为 1。检查发现就绪条件存在确定的歧义：它将任意 sing-box 子进程 PID 变化和原有用户仍可访问视为更新完成，`sing-box check` 临时子进程与旧内核上的有效响应也可能满足这个条件。原探针没有记录失配 PID 的命令行，不能把这个推断写成直接捕获到的根因，也不能据此判定产品更新失败。原失败报告完整保留，**不计作整体通过**。

第二轮只重跑受影响的更新片段，使用独立 `updates-run-02` 目录。每一轮的新 UUID 先证明更新前认证失败，再等其更新后收到真实响应；继续核对旧 UUID 拒绝、保留用户可用、稳定 PID 和文件/FD 清理。6 轮通过。首轮已经完成的稳态/TCP 数据和第二轮通过的更新数据分别引用；生产源码未为探针修正而改变。

编译的 44 个 Rust/build 文件、本地同名源码、旧/优化二进制和 sing-box 哈希已重新验证。原版本独立静态审查保持适用；本次新增测量探针为自检，未声称经过新的独立审查。
