# Rust 性能与稳定性优化记录

2026-10-02，在指定美国测试机的独立实验目录，完成了当前 Rust 单节点控制程序的优化前后比较。本轮降低了二进制体积、控制线程数量、无变化同步的堆分配以及大用户集轮询开销，并修复了 HTTP 请求卡住时停止响应迟缓的问题。

这是 **Rust 旧版本与本轮优化版本** 的比较。协议转发仍由外部 sing-box 执行，尚未完成 Go/Rust 全功能差分、生产面板验收或长期稳定性测试。

随后完成了独立目录中的 [Linux 复验与下一轮优化定位](RUST_LINUX_RECHECK_ZH.md)：每版 90 秒资源采样、256 连接保持 10 秒、1024 次真实传输，以及 6 次 10000/20000 用户更新。新发现的配置生成内存峰值和更新连接中断分别记录，不改写下方原轮次的数据。

## 修改了什么

1. **双 304 快路径**：面板配置和用户均未变化时，直接在事务锁内核对已提交快照 generation 与内核状态；取消用户表复制、重复校验、排序和哈希。内核在 HTTP 进行期间退出时仍复制成功快照并恢复，不能因走快路径漏掉健康检查。
2. **变更候选的所有权**：新增 `AppliedSnapshot::new` 对已拥有的配置和用户表校验，减少为了构造候选而重复复制用户表。部分 304、取消提交和失败重试仍保留 generation/ETag 一致性处理。
3. **控制运行时资源**：可执行程序使用 Tokio current-thread，阻塞线程上限为 2。内核检查、启动、回滚和串行事务仍放在阻塞 worker；协议转发不在该异步主线程内执行。库测试需要的 multi-thread 功能放入开发依赖。
4. **小型 WS 提示**：运行时仅接收目标节点的 `WsHint`，队列容量从 64 个完整事件改为 1 个节点通知。队列已满时合并同节点重同步提示，不存用户列表、不因重复通知断开。公开的完整 `WsClient::run` 接口仍保留原事件分发行为。
5. **及时停止**：运行循环优先响应停止并取消未完成的 HTTP 同步；离开循环立即设置 closing，之后等待 WS 与串行内核事务，防止迟到激活。停止仍可能等待正在执行的有界内核检查/启动事务。
6. **构建体积**：release 使用 Thin LTO、单 codegen unit 和符号剥离，保留 `panic = "unwind"`。另提供 diagnostic profile 保留符号与行号，用于排障。

release 与 diagnostic 命令：

```bash
cargo build -p node-runtime --release --locked
cargo build -p node-runtime --profile diagnostic --locked
```

上述 profile 和运行时选项的语义分别可查 [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html) 与 [Tokio Builder](https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html)。本轮测得的体积变化包含构建选项和源码改动，未单独拆分各项贡献；没有为减少体积改为 panic abort。

## TCP、内核内存与吞吐

同一官方 sing-box 1.14.0 二进制，所有服务端、VLESS 客户端和 origin 均为回环地址。两版内核都用 `GOMAXPROCS=2`，保持资源条件一致；这是实验设置，没有修改生产配置。

256 个请求必须同时到达 origin，保持 3 秒后逐一核对内容。两个用户规模、两个程序版本共四组，全部成功。保持阶段内核约 1034 个打开 FD；这不是最大连接数测定，也不是“每个用户都同时连接”的测试。10000 是配置中的合成用户数量。

| 用户规模 | 优化前内核空闲 RSS | 优化后内核空闲 RSS | 256 连接时内核 RSS（前 / 后） |
| --- | ---: | ---: | ---: |
| 1 | 51.77 MiB | 52.15 MiB | 58.01 / 58.21 MiB |
| 10000 | 55.86 MiB | 55.66 MiB | 65.16 / 64.17 MiB |

数据面空闲 CPU 在这组窗口内记录为 0 ticks；它低于本次采样可分辨范围，不代表实际零消耗。内核 RSS 没有呈现与控制程序相同幅度的下降。

吞吐夹具每轮并发 8、32 次请求，每次有效内容 256 KiB，共 8 MiB，重复三轮，核对完整内容：

| 用户规模 | 优化前吞吐中位数（范围） | 优化后吞吐中位数（范围） |
| --- | ---: | ---: |
| 1 | 93.89（79.26–124.63）MiB/s | 121.35（100.44–132.51）MiB/s |
| 10000 | 106.95（88.23–119.91）MiB/s | 98.77（86.08–112.31）MiB/s |

两个规模的变化方向不同且范围重叠，本轮**没有证明 TCP 吞吐提升**。短时间回环结果包含 Python 线程池/origin、客户端与共享宿主调度成本，不是公网速度。P50/P95 与各轮原始数值保存在 JSON 中，未将这些短样本用于容量规划。

下一轮要提高 TCP 吞吐或连接上限，应单独测数据面：固定速率、长连接、连接建立/关闭、socket/FD/内核 CPU 与缓冲区，同时完成其他协议客户端验证。本轮没有更改宿主 BBR、sysctl、FD 上限、DNS、证书、生产监听或服务配置。

## 稳定性验证

- Windows 本地 workspace：71 项通过；严格 clippy 与格式检查通过。
- Linux ARM64 release workspace：71 项通过；另外 1 项显式真实 VLESS 集成测试通过；fmt、clippy 与构建通过。默认测试中的真实内核项仍标为 ignored，显式执行才计入结果。
- 优化版可执行程序重复了 9 项验收：HTTPS 面板认证、真实 VLESS 转发、用户替换、304 保持原内核、拒绝未实现限制时保留有效配置、实际内核 SIGKILL 后恢复、SIGTERM 回收与文件权限等。
- 新停止回归先在旧源码复现失败：HTTP 卡住时超过 2 秒仍未关闭；本轮测试通过。真实可执行程序在 HTTPS 双 304 请求被刻意卡住时，SIGTERM 后约 16 ms 退出，子进程、监听和候选文件均清理。
- 在 HTTP 请求已经开始、尚未返回双 304 时杀掉真实内核，优化版恢复成功，并通过实际 VLESS origin 响应判断就绪。
- 有效 TLS 的 WSS 实验：其他节点提示忽略；32 次各含 10000 名用户的提示不造成断线；采用 REST 中的用户 id=2、拒绝 WS 保留而 REST 删除的 id=1；主动断线后重连、再次 REST 同步和真实业务成功；停止约 17 ms，子进程/端口/文件清理通过。
- 夹具使用独立进程组，额外执行“杀掉 leader 后遗留 child”的恢复探针，finally 清理后没有本次仍存活的组成员。

独立审查覆盖本轮准确源码及实验脚本，没有确认剩余阻断；审查是静态代码审查，网络结果来自上述实际执行。完整本地证据在 `.Codex/evidence/perf-independent-review.md` 与 `.Codex/evidence/perf-us/`，不随干净源码包携带 SSH 工具或私密运行文件。

首轮夹具在内核替换后只检查新 PID 就发起请求，产生 `ConnectionReset`，并未证明恢复失败。已改为有界等待真实业务成功；原始失败和修正后完整结果同时保留。另一次启动脚本因 CRLF 在 Bash 启动前失败，已改为 LF；没有把失败记录计作 PASS。
