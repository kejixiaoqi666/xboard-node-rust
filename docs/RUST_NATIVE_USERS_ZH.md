# Rust 用户热更新：连接连续性与资源验证

本文是早期外部 Go 内核热更新阶段的冻结报告；当前默认服务端已为 Rust，并增加 UDP、限速和来源 IP 名额。最新功能与测试见 [项目首页](../README.md)。下文默认内核与资源数字只描述当时版本。

2026-10-02 在指定美国服务器的独立回环测试目录，完成可选用户热更新片段。当前结构是 **Rust 控制层 + 外部协议内核**：默认模式继续使用官方 sing-box；新增 `xbord-native-users` 是单独的 Go 可执行文件。协议转发尚未改写为纯 Rust。

本片段解决用户列表更新时的连接中断。原生模式的 VLESS TCP、VLESS 文件 TLS、Trojan 文件 TLS 各 64 条既有连接均完整返回，正在传输的 2 MiB 内容也跨过首个用户发布点且校验一致。默认重启模式的对照仍为 0/64，并中断传输。监听、协议、TLS 等非用户配置变动仍需完整重启；本结果不是所有变更都无中断的承诺。

机器可读结果在 [rust-native-users-20261002.json](../benchmarks/results/rust-native-users-20261002.json)。复现脚本为 [native_users_lab.py](../benchmarks/native_users_lab.py)，配置为 [runtime-rust-native.json](../examples/runtime-rust-native.json)，构建及许可证见 [内核说明](../kernels/native-users/README.md)。

## 实现

官方 sing-box 1.14.0 的 RPC 接口没有用户表更新方法。已有定制分支提供 `UpdateUsers`，但认证映射直接替换、认证身份依赖用户列表下标，不能直接用于并发更新。本实现固定依赖版本，在私有副本中修改六个源文件，保留完整上游来源和哈希；不修改共享 Go 模块缓存及原 Go 节点。接口范围依据 [官方 API 配置](https://sing-box.sagernet.org/configuration/service/api/)，具体修改与上游文件哈希见 `kernels/native-users/patches/manifest.json`。

1. **完整校验后一次发布**：认证用户/flow 映射组合成不可变快照，使用 atomic pointer 发布；读者取得同一代快照，不读写共享可变 map。
2. **稳定认证身份**：认证上下文保存用户 name，即 Rust 生成的用户 ID 字符串，不保存列表下标。排序、增删之后，已经认证的连接仍对应原用户。
3. **阻止歧义认证**：重复 ID、重复 VLESS UUID（含大小写别名）、重复 Trojan 密码、非法结构及未支持设置在发布前拒绝。Trojan 认证头使用完整读取，允许合法 TCP 分片。
4. **有界控制与提交**：Rust 预检查候选配置，再通过私有 Unix socket 发送原/新 SHA-256。内核核对原摘要、候选摘要和所有非用户配置。单次 RPC 最多两秒，回复最多 8 KiB；候选仍有编码后 16 MiB 上限。
5. **确认丢失可核实**：没有收到可靠确认时另做一次有界状态查询。新摘要才提交，旧摘要保留旧成功快照，未知状态终止不确定内核并恢复上一份成功配置。未知状态恢复会中断该内核的连接。
6. **私有文件与退出**：新状态目录 0700、候选文件/socket 0600；每次运行生成自己的 socket，拒绝覆盖已有路径。关闭先回收控制循环，再关闭内核，Rust 回收子进程及本次文件。面板 Token 不传给协议内核。

删除用户会禁止新的认证，已经认证的连接可以继续。这是当前明确的连接连续性语义，尚未提供“删除用户即强制断开其全部会话”。整个 Rust 控制程序的成功快照仍在内存中，控制程序重启后需要面板；跨进程持久恢复未完成。

## 验证方法与版本

主机为 Debian 13 / Linux ARM64。Rust 1.98.1，Go 1.26.8；官方 sing-box 1.14.0 同时作为默认服务端和真实客户端。新增内核固定 cedar2025/sing-box `2e665cb7e295` 及 sing-vmess `3aed155119a1`，只注册当前所需协议和 direct/DNS 基础模块。

所有面板、目标服务和客户端连接都在回环地址。面板是有效证书的 HTTPS 夹具，用户/Token 是合成数据；TLS 测试使用有效证书链及主机名验证，错误主机名必须被拒绝。没有替换现有节点或修改全局 DNS、hosts、TCP/FD 设置。测试使用的证书在原路径读取，不进入交付包。

| 项目 | 结果 |
| --- | --- |
| Windows release workspace | 78 项通过；另有真实内核测试默认 ignored |
| Linux release workspace | 81 项通过，含 3 项 Unix 摘要确认/异常帧测试 |
| fmt / strict clippy | Windows、Linux 通过 |
| 显式官方真实 VLESS 集成 | 1 项通过 |
| Go 内核单测 / race | 7 项通过；含并发认证与 1000 次快照发布、稳定身份、失败不部分发布、Trojan 分片认证 |
| 产品源版本绑定 | 63 个 Rust/内核/构建输入文件哈希一致，独立只读静态审查通过；执行结果单独记录 |

实际验证的 Rust 二进制为 3,741,624 B，SHA-256 `3cb2bccf790db8e2680cf13602ce2ba3514f7b50b510f43c7f278e35b14106a9`。新增内核为 13,893,794 B，SHA-256 `92374e7e5baf1133f363016edaef0bf1e0b613f05cd4b8c7430ccf3b06de5242`。本次 Rust 体积与前一轮流式配置版相同，代码/哈希已经变化。

63 文件构建清单 SHA-256 为 `c4bea550d9817c54dc8c0b4a374849c20bd72183317d0f003f9eba0f0aaa2ac4`，构建输入压缩包 SHA-256 为 `75bf7330b743db5b1496c46116bf4c43b2df40efcfc6b4316ee288b0f10d8343`。干净完整源码包还包含说明和测量脚本，这些附加文件不假称参与产品编译。

## 用户更新、认证和传输

| 场景 | 更新次数 | 既有连接完整返回 | 更新中的 2 MiB 传输 | 认证结果 |
| --- | ---: | ---: | --- | --- |
| 默认 VLESS 重启 | 6 | 0/64 | 中断，符合对照预期 | 新用户可用、被删用户新认证拒绝、保留用户可用 |
| 原生 VLESS | 6 | 64/64 | 完整且字节一致，跨首个发布点 | 同上；内核 PID 保持 |
| 原生 VLESS TLS | 1 | 64/64 | 完整且字节一致 | 同上；错误 TLS 主机名拒绝 |
| 原生 Trojan TLS | 1 | 64/64 | 完整且字节一致 | 同上；含中文/Unicode/转义字符密码 |

VLESS 的六轮在一万/两万用户间交替，每轮使用唯一新增凭据；新增前必须认证失败，更新后必须认证成功。64 条保持连接各有 32 条来自保留用户和被删除用户，贯穿六轮更新后逐个核验响应体。2 MiB 流验证跨首个发布点，没有宣称跨过全部六轮。

面板仅反转列表的案例不重启内核。Rust 本来按用户 ID 归一排序，该案例证明输入顺序变化不触发重启；实际认证表并发重排后身份稳定由 Go `auth_test.go` 与 race 测试支持。

从设置夹具的新用户集，到观察真实客户端认证成功，默认六轮约 1.15–1.59 秒，原生六轮约 0.49–1.47 秒。此时间包含一秒轮询、HTTPS 拉取、预检查、客户端重试和调度，并非原子发布函数延迟。没有从这些小样本宣称固定更新时间或 CPU 降幅。

## 资源：明确比较范围

以下对照使用同一 Rust 程序、一万用户、相同回环夹具和 `GOMAXPROCS=2`，每版稳定采样约 30 秒；随后交替一万/两万用户六轮。对比对象是 **全功能官方 sing-box 与限定协议的定制内核**，上游快照、注册功能和补丁都不同。这不是同一协议实现的单因素优化，也不是 Go 节点与 Rust 节点的性能对比。

| 指标 | 默认官方内核 | 可选定制内核 |
| --- | ---: | ---: |
| 协议内核文件 | 75,759,845 B | 13,893,794 B |
| Rust 控制程序文件 | 3,741,624 B | 3,741,624 B |
| 控制程序常驻 RSS 中位数 | 6.63 MiB | 6.64 MiB |
| 协议内核常驻 RSS 中位数 | 56.22 MiB | 20.87 MiB |
| 控制线程 | 2 | 2 |
| 控制程序六轮后的 VmHWM | 15.03 MiB | 13.72 MiB |
| 控制/子进程 RSS 求和采样峰值 | 160.43 MiB | 99.97 MiB |

协议内核常驻 RSS 在此夹具约低 62.9%，体积约小 81.7%，收益以精简功能范围为前提。两版控制程序 CPU 约为单核 0.10% / 0.07%，协议内核稳定窗口均为零计时 tick；窗口短且负载低，不能推导“零 CPU”或稳定的 CPU 改善。

更新采样器扫描 `/proc` 后等待 10 ms，实际间隔还包括扫描耗时；历史 m5 记录中的 `interval_seconds` 实际是等待时长，新脚本已改名 `poll_delay_seconds`。进程组 RSS 求和包含临时预检查子进程，最多观察到三个进程；它不是物理独占内存，亦不能捕获所有瞬时峰值。已退出检查进程的两个采样被显式跳过，采样线程错误必须使验证失败。控制程序 VmHWM 单列，不能拿它代替全部协议进程的峰值。

## TCP 与恢复

- 512 用户，256 条真实 VLESS 连接同时保持 10 秒，逐条响应内容正确。
- 内核 FD 从 10 增至 1034，完成后回到 10；控制程序 FD 保持 10。保持期间内核 RSS 约 22.19 MiB。
- 8 并发、1024 次 × 256 KiB，全部内容一致；该次回环传输约 2.05 秒，即 124.95 MiB/s。没有配对吞吐优化结论，不作为公网速度或最大承载证明。
- SIGKILL 内核后，用旧成功用户认证确认恢复；候选文件实际收敛为一份约需额外 0.051 秒。
- 修改监听端口触发完整重启，新端口真实认证成功，旧端口关闭。
- REST 请求卡住时 SIGTERM 正常退出约 0.008 秒，子进程、候选/socket 清理通过；该样本不作为保证时延。

四种控制故障另行验证：实际内核应用后丢确认，查询新摘要后提交；返回拒绝，旧进程/旧用户保留且继续重试；实际应用后伪造未知摘要，终止并从旧成功快照恢复，新增用户不得泄露至恢复配置；替换和查询均卡住时有界退出。m7 丢确认/未知状态两例均记录真实内核 `real_applied=1`。

## 失败证据与复测

首轮 m4 功能案例通过，但采样器读取刚退出进程时产生 `VmRSS` KeyError，因此资源证据标记 UNVERIFIED，未用于上述对照。修正后 m5 完整采样和四个协议/控制故障案例通过，但整份报告仍保留 FAIL：父进程有 100 ms 的启动稳定窗口，认证可能在提交前已经可用，立即断言“只剩一个候选”过早。

没有修改产品源码或覆盖原失败报告。改为在实际认证可用后等待候选回收最多三秒，m6 定向生命周期复测通过；m7 另行复测四故障并增加“内核确已应用”的直接断言。当前结果聚合明确采用 m5 的四协议/资源、m6 的生命周期、m7 的控制故障，三次使用同一对二进制。它不把 m5 改写为整套 PASS。

## 交付与后续

Linux 包含原始验证的 ARM64 二进制、两种配置例子、构建和源码清单、完整仓库源码及协议内核的 vendored 对应源码/许可证。Rust GNU 二进制需 glibc 2.39+、libgcc_s；CGO=0 的协议内核未发现动态 NEEDED 库。不是 x86_64、Windows 或通用 Rust 静态包。

Rust 控制层继续使用现有 MPL-2.0；新增外部内核按 GPL-3.0-or-later 及保留的上游条款提供。详见 [NOTICE.md](../kernels/native-users/NOTICE.md) 和上游许可证。vendored 源码仅把本机构建 replacement 路径改为相对路径，Go 源码保持验证版本；离线 test/build 的产物不替换已经验收的原二进制。

当前未完成：真实流量计费与可靠上报、限速/设备/IP 执行、REALITY/其他协议、自定义路由/DNS、多节点、控制程序持久恢复、生产面板兼容。下一片段应优先接真实内核计数，覆盖计数重置、失败保留、重试及重复计费边界，再做限制执行。没有上线生产或提交/推送 Git；本次是有限回环验收，不是最大 TCP 容量、公网链路或长时间稳定性认证。
